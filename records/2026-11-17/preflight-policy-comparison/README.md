# ROS1/ROS2飞前检查与当前定位时效

本轮回答“缺失检查是否过严或ROS2通信异常”。用户随后明确电量、遥控器暂时不管，二者移出本轮处理范围。仅只读对照、取样，没有改阈值、启停定位/转发/服务、替换正式源码或调用飞控控制接口。

结论：当前r4与ROS1使用相同显示判定和逐话题时效。定位输出确实间歇变旧，转发确实变稀疏；本次没有发现整体DDS通信中断或这些小消息的QoS不匹配。主要延迟发生于FAST-LIO发布测量之前，与已取证的误同步问题一致。不同红色状态应分别解释。

## 规则对照

ROS1使用2026-11-16审计原始快照与本机原工程，ROS2同时核对canonical和实际r4包。四处preflight_status.py均字节相同，SHA256为6f06e6d9496b7ff5bab2006ee838e268137160782308d4aa6b924129cd5f3829。AST提取全部逐话题限值也相同，r4采样器与canonical相同。见policy-comparison.json与comparison-sources.tar.gz。

| 检查 | ROS1与当前ROS2共同规则 |
| --- | --- |
| 雷达/IMU/LIO/点云/外部位姿/飞控里程计 | 源帧龄、接收帧龄均≤0.4s |
| 飞控状态/着地/EKF | ≤3s |
| 整体监视失效 | 2.5s |
| 发布来源、坐标系、位姿有效性 | 检查 |
| EKF | 姿态、水平/垂直速度、相对水平位置、绝对垂直位置有效，无GPS/加速计错误 |
| 频率 | 显示实测接收频率，不以30Hz为正常门槛 |

显示0.4秒与实际转发0.2秒是不同门槛。ROS1原地面站内附转发源码也有0.2秒测量时效、保留源戳、每个源戳只发一次的逻辑；ROS2安装版保留该策略。另有旧机实际只读证据：.235定位10.044Hz、外部位姿9.990Hz、飞控回传约30Hz，见../../2026-11-16/pose-chain235-observation.json。publish_rate=30仅是上限配置，不能把它当实测频率或重盖源戳凑频率。

EKF状态约1Hz持续到达，28条中16条pos_vert_abs_status_flag=false。“估计无效”来自收到的飞控有效性标志，不是该话题断流。未将这一标志直接等同于某一种融合源丢失，未改飞控参数。电池/RC仅保留采样的原始证据，按用户要求暂停处理，不作为本轮定位修复阻塞条件。
