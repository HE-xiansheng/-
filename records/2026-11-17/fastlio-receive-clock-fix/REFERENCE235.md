# .235 与 .224 的行为差异

本次只读核对 .235 的当前文件、运行进程和已保留日志，没有启停该机任何模块。当前源文件 SHA256 为 `87d38041d0b1e8348bcae5ff3b2e4367fe3e3376b547fd8e9295568901ab3cef`；ROS Noetic 的 roscpp 为 `1.17.4-1focal.20250519.224856`。

| 项目 | .235 ROS1 源码/环境 | .224 故障版 | 联合候选 |
| --- | --- | --- | --- |
| 消息传输 | ROS1/TCPROS，无 Fast DDS 读者历史恢复 | Humble/Fast DDS 2.6.12 / rmw_fastrtps 6.2.10 | 保留 ROS2；针对 IMU 改接收策略 |
| IMU 订阅缓存 | 200000 条 | Reliable / 10 条，200 Hz 仅约 50 ms | Best Effort / 400 条，200 Hz 约 2 s |
| LiDAR 订阅缓存 | 200000 条 | Reliable / 20 条 | 本轮候选保留 20 条，另验真实点云负载 |
| 回调与解算 | `ros::spinOnce()` 后解算，循环配置 5000 Hz | 单线程 executor，100 Hz 解算 timer，消息在下层排队 | 尚未更改线程模型，必须通过真实负载/恢复验证 |
| 自同步判定 | 最后执行的两个传感器回调戳相差 >1s 时固定补偿 | 同一脆弱逻辑 | 比较 DDS 发布时刻与测量时刻的稳定差值，已对齐也锁定 |
| 正常状态规则 | 原地面站门槛 | 与 ROS1 相同 | 保留原显示/转发门槛和测量源戳 |

ROS1 的 `spinOnce()` 调用全局 callback queue 的 `callAvailable()`；后者移入当前队列并处理这批待执行回调。可直接核对本目录保存的官方 roscpp **1.17.4** `init.cpp` 和 `callback_queue.cpp`。ROS2 Humble 官方文档指出：当回调处理时间较长时，消息在下层队列等待，executor 从 wait set 得到的是“是否有消息”，堆积情况下按轮询处理，并不保证跨话题 FIFO。已保存官方文档源码与片段，见 `ros2-executor-reference.json`。文档站点返回过机器人验证页，未把该页面当作技术证据；使用的是官方 `ros2/ros2_documentation` Humble 分支源码。

这解释了旧使用方式为什么更不容易触发本次故障：较大的接收缓存和不同的批量处理方式减少了短暂停顿后的消息丢失/交错；ROS1 也没有本次复现的 Fast DDS Reliable 历史交付路径。迁移时改成小缓存，却保留了依赖回调执行顺序的同步公式，改变了实际运行行为。当前已复现的正负假偏移都不是配置中真实标定的设备时差。

但不能声称 .235 的旧算法永远不会出问题。其源码仍包含同样的 `last_timestamp_lidar + 0.1 - last_timestamp_imu` 公式，单流长时间停顿也具备误判条件；本次 .235 没有正在运行的 FAST-LIO，也没有找到可核对的历史 FAST-LIO 运行日志。此前保存的正常窗口只能证明当时链路正常，不能证明所有历史工况都没有触发。此处区分源码/环境差异与已经实测的因果，不把缓存差异说成唯一原因。

联合候选的验收还需同时覆盖输入恢复、点云消费者、真实飞控持续融合和地面站状态。正式安装完成前，本文件不声称这些检查已经全部通过。
