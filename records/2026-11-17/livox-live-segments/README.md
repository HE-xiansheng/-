# 实采链路分段诊断：仍未通过实时验收

在不停止旧机服务、不改变新机正式入口的前提下，继续定位上一轮无线实时转发的时龄和间断问题。所有ROS2输出仅domain183/localhost；无真实飞控输入，所有源测量时间戳保留。

## 观测与对照

- run6（60秒，旧机→电脑→新机SSH）：严格18/29。旧机发送队列中位约9.6秒，最大约13秒；点云开始发送到电脑读完整帧中位1.61秒。新机接收后队列/发布中位约5.27ms，定位时龄最大14.40秒，转发拒绝旧观测。该轮不支持把主要积压归因于新机消息解码。
- run7（30秒，进一步拆分压缩/管道写入）：严格21/29。点云压缩中位17.03ms，写SSH管道中位3.83ms，但从旧机开始发送到电脑读完整帧中位1.075秒、最大2.395秒；旧机队列最大0.980秒、新机排队/发布中位5.03ms。定位最大时龄2.374秒，转发无有效输出。不能仅凭源端write很快就认定数据已被目的端及时收到。
- run8-direct（60秒，旧机→新机临时TCP直连）：严格19/30。电脑只负责启动与取证，数据不经电脑；新机仅在192.168.1.224:24383监听一次，验证对端.235和随机单次64字符令牌，实测鉴别通过。点云压缩中位18.35ms、socket写中位0.896ms，但一次socket写阻塞11.533秒，旧机队列中位11.98秒/最大16.31秒，并实际发生队列丢弃，定位时龄最大16.66秒，无有效转发。此失败否定“只要绕过电脑中转即可解决”的推断。TCP对照不作为生产接口，不提供永久监听、ROS跨网或控制接口。

两轮SSH与直连都保留完整检查结果，不放宽源时龄/间断/零丢弃门槛。这里的统计只能定位观察到的积压段，不足以将全部延迟唯一归因于AP、无线干扰、内核缓冲或TCP策略；也不能据此认定原生有线雷达驱动失败。

## 时钟与网络只读证据

首次逐次SSH启动的时钟测量包含握手、界限很宽，保留clock-offset-bounds.json，不用于毫秒结论。随后同一持续SSH连接内往返测量排除握手：.235相对电脑约-64至-62ms、.224约-62.5至-61.0ms；两台机载相差毫秒级，不能解释多秒积压。分段报告未暗中平移时间，跨电脑的负约60ms应按该偏移解释，不能认定为负传输时延。源内排队/编码/写入和目标内排队无需跨机时钟修正。

最终两机iw均Power save: off；旧机即时信号约-74dBm/tx51.5Mbit，新机约-60dBm/tx172Mbit。这些是一次即时读数，不能据此证明整段实际吞吐或单独根因；未改WiFi、路由、功耗或驱动。
