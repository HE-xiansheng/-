# 实物云台视频经临时SSH转发验证

旧机.235保持原服务与网络不变，读取其已有MediaMTX端口8554。电脑只在loopback端口21654转发旧机8554，再将新机loopback18655反向转发到电脑21654。新机使用临时配置将该流转发到loopback18554，并运行真实MPP ROS2解码器。电脑另用临时SSH本地端口11954读取新机18554，执行与Qt相同的GStreamer参数。所有隧道、测试观察器、relay和解码器均为本阶段所属进程，不启用systemd服务。

这是实物视频验证，路径仍经过旧机；不是新机云台物理网卡/直连网络验收。没有云台运动命令、飞控连接或飞行任务。只记录元数据和稀疏像素摘要，不保存摄像头图像。

## 接收漏帧与源戳结论

初轮Python和后续C++观察器都无法逐一配对所有灰度/彩色帧。仅增大接收队列没有解决。此前直接用配对比例98%门槛可能混淆观察漏帧与改戳，run1/run2/run5失败保留；run3的中间通过仅代表该次比例超过门槛，不作为最终源戳证明。

本阶段增加默认关闭的rtsp_hw_pub_ultra.frames子logger，在DEBUG时记录每次实际发布消息的header stamp，正常INFO级别不输出帧日志。run6用此发布端独立记录逐条核对：

- 941个灰度、456个彩色发布源戳唯一。
- 所有彩色发布源戳均存在于对应灰度发布记录中。
- C++实际收到的全部灰度/彩色源戳都在相应发布记录中精确存在，未发现改戳。
- C++观察窗口内应有935条灰度、453条彩色，实际漏收88条和3条。订阅端仍有漏帧，这项性能问题没有修复，也未归因到具体DDS或调度组件。

因此最终20项通过证明视频能读、解码输出格式正确及收到的时间戳对应真实发布记录，**不证明无丢帧或持续吞吐已验收**。源戳配对问题与接收漏帧分别记录，不通过降低接收完整性门槛掩盖后者。
